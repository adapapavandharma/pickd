How this was built

The parts that were actually hard

Anyone can put a product grid on a page. These are the five problems underneath it that took real decisions — including the three bugs that shipped before they were caught, which are the more useful half.

Every claim here is checkable against the source, and the terminal output is copied from the runs, not written for the page.

01

Getting product photos out of a source that blocks scrapers

Amazon asks that images come from their API, and blocks automated page fetches anyway. So the obvious approach is both against the rules and unreliable.

The answer was a three-tier chain that stops at the first real image. If Associates API credentials exist, it uses them — the correct path, which also returns live prices. Without them it falls back to Amazon's per-ASIN image endpoint, which is what their own SiteStripe embeds resolve to. For non-Amazon merchants it reads OpenGraph tags.

The trap is that Amazon does not return a 404 for a missing image. It returns a roughly 43-byte transparent GIF with a 200 OK, so a naive fetcher happily saves a blank file and the grid fills with invisible products. The fix is to check magic bytes and size rather than status code:

scripts/extract.mjs
/* Amazon serves a tiny transparent GIF for "no image". Reject those. */
function isRealImage(buf) {
  if (!buf || buf.length < 2500) return false;
  const isGif  = buf[0] === 0x47 && buf[1] === 0x49 && buf[2] === 0x46;
  const isJpg  = buf[0] === 0xff && buf[1] === 0xd8;
  const isPng  = buf[0] === 0x89 && buf[1] === 0x50;
  const isWebp = buf.slice(0, 4).toString() === "RIFF";
  if (isGif) return false;
  return isJpg || isPng || isWebp;
}

Images are then downloaded and served locally rather than hot-linked, so a rotated CDN path cannot silently empty the shelf. The PA-API tier signs its own AWS SigV4 requests by hand — there is no SDK in this project.

02

Choosing chart colours by measurement instead of taste

A warm palette that looks right to me is not evidence that it works for someone with deuteranopia, or at 3:1 against a dark surface.

So I ran candidates through a validator instead of trusting my eye. My first palette failed — three colours were too desaturated to read as distinct hues, and two were closer together than full-colour vision can reliably separate:

attempt 1 — rejected
[PASS] Lightness band       all 5 inside L 0.43–0.77
[FAIL] Chroma floor         below floor (reads gray):
       #2d7d74 → 0.078   #4a6fa5 → 0.095   #8c4f6d → 0.090
[PASS] CVD separation       worst adjacent ΔE 8.4 (protan)
[FAIL] Normal-vision floor  #8c4f6d ↔ #4a6fa5 ΔE 13.7 — below 15,
       hard to tell apart even with full colour vision

→ FAILED

Two more rounds of re-stepping — pushing chroma up and separating the plum from the blue — got there. The palette now shipping passes every hard gate against both the light and dark surfaces this site actually renders on:

shipped palette — light surface #fffdfa
[PASS] Lightness band       all 5 inside L 0.43–0.77
[PASS] Chroma floor         all 5 ≥ 0.1
[PASS] CVD separation       worst adjacent ΔE 11.3 (deutan) · tritan 27.7
[PASS] Normal-vision floor  worst adjacent ΔE 24.9
[WARN] Contrast vs surface  #e0a41b at 2.18 — relief required

→ ALL CHECKS PASS

That remaining warning is not dismissed. It obliges the chart to carry the value another way, so every segment is directly labelled and every chart has a table-view twin — no number on the dashboard is reachable only by hovering. The dark steps are a separately chosen set validated against the dark surface, not an automatic flip of the light ones.

5 slots light + dark validated deutan · protan · tritan table-view twin on every chart
03

Three bugs that shipped before I caught them

The useful part of any build log. All three were found on the live site, not in theory, and all three are the same shape: something that fails closed.

The workflow that failed in zero seconds. The first deploy failed with no logs and no jobs. The cause was a colon-space inside an unquoted YAML scalar — legal JavaScript, illegal YAML:

.github/workflows — the broken line
run: node -e "... throw new Error('incomplete product: ' + id) ..."
                                                  ↑ ends the scalar

The fix was to stop cramming a program into a YAML string. That check now lives in scripts/validate.mjs, where it also runs locally and does considerably more: required fields, duplicate IDs, images actually present on disk, price types, and a warning for any Amazon link missing its affiliate tag.

Cards that were invisible unless JavaScript won a race. Products were hidden at opacity:0 in CSS and only revealed by an IntersectionObserver callback. Any failure of that callback — a script error, a blocked observer, a tab the browser never paints — left the entire shelf blank with no way to recover. A scroll animation had been given the power to delete the content.

Cards are now visible by default. The reveal is opt-in behind a class that JavaScript only adds once it has a live observer, plus a timeout that removes the class outright rather than starting a transition — because a tab that is not painting will not advance transitions either:

assets/js/app.js
document.documentElement.classList.add("js-reveal");

// If the observer has not reported within 1.2s, drop the reveal entirely.
const failsafe = setTimeout(() => {
  document.documentElement.classList.remove("js-reveal");
}, 1200);

Fresh HTML served with a stale stylesheet. Caught live. GitHub Pages sets max-age=600, so for ten minutes after a deploy a returning visitor could get the new page and the previous CSS. In this case that combination reproduced the invisible-cards bug exactly — the old stylesheet still hid cards unconditionally while the new script no longer added the class it keyed on.

Assets are now stamped with a hash of their own contents, so a URL changes exactly when the file does and unchanged files stay cached. It covers a second level most implementations miss: ES module specifiers are fetched independently of the page, so a stamped app.js is worthless if the analytics.js it imports comes from cache.

deployed output
index.html      styles.css?v=ac364028   app.js?v=1a1c3288
dashboard.html  dashboard.css?v=14fff9d0  dashboard.js?v=c0c66355
app.js          import "./analytics.js?v=9da3dafb"
04

Charts with no charting library

Every mark on the dashboard is SVG this project draws itself. Not for purity — for the ~90 KB and the control.

A charting library would have been faster to write and harder to hold to a standard. Drawing the marks directly means one spec applies everywhere and can be checked in the rendered DOM rather than trusted:

measured in the live page
categoryBarWidths   [24,24,24,24,24,24,24,24,24,24]  cap 24px
topBarHeights       [24,24,24,24,24,24,24,24,24,24]
stacked-bar gaps    [2,2,2,2]                       surface, not strokes
gridline dasharray  none                            hairline, solid
line stroke-width   2
axis text fill      rgb(133,122,112)                muted token, not series colour

Bars capped at 24px so the band keeps its air, 4px rounded data-ends squared at the baseline, a 2px gap in the surface colour doing the separating rather than a stroke drawn around each mark, and area fills at 10% opacity — a wash, never a saturated block. Text never wears the data colour; identity comes from the swatch beside it.

The interaction layer is the part libraries usually get wrong: the time-series chart has a crosshair with a tooltip and an arrow-key equivalent, focusable and announced, because a tooltip that is the only route to a value excludes anyone not using a mouse.

05

Two JSON files, twenty pages

The catalogue is the source of truth. Product pages, guides, the index, the sitemap and the navigation are all downstream of it.

Adding a product means adding a line to data/links.txt and running the extractor. Everything else follows: a product page with structured data, its appearance in any guide that references it, the cross-links in both directions, and a sitemap entry.

npm run build
  16 product pages
  3 guides + index
  20 pages generated, sitemap rebuilt, nav synced into 3 hand-written page(s)

The generator also owns the navigation on every page including the hand-written ones, rewriting it between marker comments — so there is exactly one definition of the nav and no page can drift out of sync as the site grows.

Asset paths are depth-aware rather than absolute, which is why a page at /p/ works identically on a project page, a custom domain, or opened from a local folder. Product pages and guides are fully rendered in the HTML — every word is there with JavaScript disabled, which is what search engines and slow connections actually get.

What this deliberately is not

  • Not a live storefront. The affiliate tag is a placeholder. Prices and ratings are sample data, and so is the entire 90-day dashboard history — it is generated from a seeded, deterministic random number generator so the numbers hold still between reloads. Real clicks made on this site are recorded and folded in.
  • Not a hosted analytics product. Click tracking writes to localStorage, which means it is per-browser and cannot be aggregated. In production that layer becomes a server; the schema and the aggregation code would not change.
  • Not tested. There is no test suite. Verification here was done by measuring the rendered DOM and the deployed output, which is honest but is not the same thing.
  • Not using PA-API. Live pricing needs an approved Associates account with qualifying sales. The signing code is written and the fallback chain is built around its absence.

All of it is readable — the extractor, the generator, the chart code and the commit history that includes each of the bugs above.
